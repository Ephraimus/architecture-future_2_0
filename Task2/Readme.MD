# Task 2 — Домены и потоки данных

## Цель

Сформировать четкую доменную архитектуру, в которой каждый бизнес-блок развивается автономно без вовлечения общего DWH,
и визуализировать основные каналы передачи информации между ними с помощью Data Flow Diagram.

## Домены

1. **Health**
    - Сервис управления ЭМК и приёмами пациентов
    - Публикация событий о госпитализациях и визитах

2. **Finance**
    - Счета, платежи, кредиты
    - Генерация финансовых операций на основе событий из Health и партнерских доменов

3. **Pharma**
    - Заказы, остатки и маршрутизация лекарств
    - События о пополнении запасов и выполненных заказах

4. **Electronic**
    - Заказы и запасы электронного оборудования
    - Интеграция с партнёрами по поставкам техники

5. **Self-Service & BI**
    - Портал для аналитики и отчетов
    - BI-дашборды и ML-модели, потребляющие данные через единый API

---

## Логика разделения

- **Бизнес-ориентированность**  
  Каждый домен отражает реальное направление компании и обслуживает свой набор сущностей и процессов.

- **Автономность разработки**  
  Команды могут менять внутреннюю реализацию своего домена, не затрагивая остальные.

- **Event-driven интеграция**  
  Домены обмениваются данными только через **Kafka / Pulsar** и единую **Data Mesh API**, без прямых запросов к DWH.

- **Изоляция от DWH**  
  Исторический DWH остаётся в read-only режиме, вся новая логика уходит в доменные сервисы и Data Lake.

## Преимущества

- **Независимость**
  Изменения в одном домене не требуют модификации других или DWH.

- **Гибкость интеграции
  Появление нового направления (например IoT-домен) сводится к публикации/подписке на события в Kafka.

- **Производительность
  Аналитика и отчёты строятся поверх Data Mesh API, без нагрузок на DWH.

- **Управление доступом
  Единая точка доступа через Mesh API позволяет централизованно контролировать права.

- **Упрощённое тестирование
  Междоменные контракты закреплены в событиях и API-контрактах, что сокращает регрессионные риски.
