# Обновление архитектуры на следующий год

В текущей системе выявлены ограничивающие факторы, которые мешают быстрому росту и интеграции новых направлений. Для
достижения высоких показателей необходимо сфокусироваться на стратегических приоритетах и устранении препятствий.

## Стратегические приоритеты

- Гарантировать масштабируемость медицинских, финансовых, фармацевтических и электронных сервисов
- Сократить время подготовки отчётов и аналитики до нескольких минут
- Упростить подключение новых подразделений и партнёров
- Разграничить зоны ответственности между бизнес-доменами

## Основные барьеры

### Технологические ограничения

- **Монолитное хранилище** на устаревшей платформе сильно загружено и плохо поддаётся изменениям
- **Устаревшие инструменты** сложно масштабировать и обновлять

### Интеграционные сложности

- **Ручная шина данных** требует длительной поддержки и тормозит подключение новых систем
- **Смешение доменов** в одной базе повышает риск некорректных изменений

### Доступ и доверие

- **Отсутствие self-service**: бизнес зависим от IT-команды при создании отчётов
- **Фрагментарная авторизация**: нет единого контроля прав доступа
- **Дублирование логики**: несколько команд реализуют одинаковые алгоритмы, падает доверие к данным

### Операционные риски

- **Неунифицированный подход** к расширению партнёрской сети замедляет запуск новых интеграций
- **Высокая зависимость** от монолита при добавлении новых бизнес-единиц

---

Предложенные изменения позволят разгрузить центральное хранилище, организовать независимые дата-пулы для каждого домена,
обеспечить быстрый доступ к данным и выстроить надёжный механизм контроля и мониторинга.

## 🏗 Предлагаемая архитектура

Описание структуры
Схема построена по пяти основным слоям, каждый из которых закрывает конкретные проблемы предыдущей архитектуры:

1. Пользователи (user)
    - аналитики, менеджеры, продажники и врачи получают доступ к данным через единый Портал, BI-платформу и ML-пайплайн.
2. Доменные сервисы (DomainServices)
    - каждый бизнес-домен (здравоохранение, финансы, фармацевтика, электроника) выпускает события в Kafka в новом
      унифицированном формате, что устраняет риски смешения данных и дублирования логики.
3. Легаси-прокси (LegacyProxy)
    - Python-контейнеры читают устаревшие сообщения из Apache Camel и CDC-потоки из DWH, конвертируют их в новый формат
      и отправляют в Kafka. Это позволяет постепенно мигрировать старые интеграции без единоразового «большого взрыва».
3. Событийная платформа (EventBus)
    - Kafka / Pulsar выступает в роли центрального обмена событиями, гарантируя масштабируемость и отказоустойчивость.
4. Data Lakehouse и Data Mesh (DataLayer)
    - все события поступают в Data Lakehouse (Delta Lake / Parquet на S3), а через MeshAPI (GraphQL / REST) становятся
      дата-продуктами. Это решает проблему монолита, разбивает данные по доменам и обеспечивает единое место для
      аналитики.
5. Self-service и безопасность (AccessLayer)
   — Портал, BI и ML получают данные через MeshAPI, а доступ регулируется Keycloak и ABAC. Бизнес-пользователи больше не
   зависят от IT-команды при построении отчётов.
6. Легаси-слой (Legacy)
   — DWH остаётся доступным только для чтения исторических отчётов, а Apache Camel продолжает обслуживать устаревшие
   интеграции до полной миграции.

### Как это решает основные барьеры

- Монолитное хранилище переводится в read-only режим, а вся новая логика идёт через Data Lakehouse.
- Self-service реализован через Portal/BI/ML поверх MeshAPI.
- Смешение доменов устранено за счёт отдельных DomainServices и Data Mesh.
- Интеграции реструктурированы: LegacyProxy плавно преобразует старые потоки без простоя.
- Устаревшие технологии постепенно заменяются контейнерными Python-приложениями.
- Фрагментарный доступ унифицирован через Keycloak+ABAC.
- Дублирование логики исключается за счёт единого API MeshAPI и каталогизации дата-продуктов.
- Расширение партнёрской сети ускоряется благодаря стандартизированному выпуску событий в Kafka и единому Data Mesh.

#### Review Update
Ранее всю логику, связанную с фильтрацией, преобразованиями и маршрутизацией сообщений, держали в едином ESB (Apache Camel). Теперь мы разбиваем эти обязанности на несколько частей, чтобы облегчить сопровождение и дать командам свободу улучшать свою область без влияния на весь монолит.

---

## Как делим функциональность ESB

1. **Прокси для «легаси-интеграций»**  
   Раньше Camel читал сообщения из разных очередей и сразу сам делал множество преобразований. Мы вводим простой Python-контейнер (ProxyQueueReader), который:
   - Подписывается на очереди Camel и получает «сырые» сообщения в старом формате.  
   - Нормализует их (приводит поля к единому JSON-шаблону, удаляет ненужные атрибуты).  
   - Публикует уже «чистые» события в Kafka.

   Таким образом мы убираем из Camel базовую фильтрацию и парсинг: вместо этого небольшой Python-сервис (где у команды уже есть опыт работы с Python и ETL) готовит данные для унифицированного формата.

2. **ETL-процессы для исторических данных**  
   Если нужно выполнить более сложную пакетную обработку «сырых» данных из старого DWH (например, объединить таблицы, вычислить новые поля, очистить данные), запускается отдельный Python-контейнер (LegacyEtl). Этот контейнер:
   - Читает «сырые» записи из DWH (через CDC-потоки или прямые запросы).  
   - Применяет бизнес-правила, агрегации, обогащения.  
   - Записывает результат в наше Data Lakehouse.(в качестве альтернативы более маштабируемой - можно сразу рассмотреть пункт 4)

   Вся «тяжёлая» ETL-логика теперь собрана в одном месте на Python, а не разбросана по запутанным Camel-роутам. Команда, которая привыкла к пакетным обработкам на Python, сможет легко вносить изменения в этот контейнер.

3. **Микро-преобразования и маршрутизация в доменных сервисах**  
   Все небольшие «если-то» правила, которые раньше прописывали в ESB, теперь островными механизмами переносятся либо прямо в код доменного сервиса, либо в лёгкое Kafka Streams приложение на Python. Например:
   - Сервис **Health** публикует событие «пациент пришёл» и самостоятельно проверяет условие: отправляет в топик `visit_approved` или `visit_rejected`.  
   - Если нужно объединить данные из нескольких топиков и превратить их в новое событие, можно завести небольшое Kafka Streams приложение, которое слушает входной топик, фильтрует/преобразует и публикует в выходной топик.

   Теперь у каждого домена (Health, Finance, Pharma, Electronic) есть возможность полностью контролировать, как формируются и куда уходят сообщения, а не менять общую конфигурацию ESB.

4. **Airflow (опционально, при необходимости)**  
   Если появятся сложные пакетные процессы (например, пересчёт агрегатов раз в сутки, группировка по нескольким источникам, оповещение BI-портала), мы можем подключить Airflow. Пока достаточно Python-контейнеров и Kafka Streams для большинства задач. Однако, если нужен удобный трекинг DAG-задач, автоматические retries и визуальная отладка, мы поднимем кластер Airflow. Команда легко внедрит его, потому что уже работает с ETL на Python.

## Вывод

Реализация предложенной архитектуры позволит:

Разгрузить монолитный DWH, переложив логику в event-driven микросервисы и ELT-пайплайны.

Предоставить бизнесу self-service портал для быстрой аналитики без участия IT.

Внедрить Data Lakehouse + Data Mesh, обеспечив прозрачность, lineage и governance через единый каталог данных.

Обеспечить безопасность и управление доступом на уровне дата-продуктов и операций.

Готовность к быстрой интеграции новых бизнес-единиц без затрагивания исторического хранилища.

Такой подход гарантирует ускорение time-to-market, гибкое масштабирование и высокое доверие к данным.
